# 根路徑 522 唯讀調查（2026-11-04）

## 已提供的證據

使用者提供：2026-11-01 前後的 Cloudflare 最近 7 天分析中，`fursay.com` 的 `/` HTML 請求有 38 次 HTTP 522（來源連線逾時），另有 92 次 403（預期的 WAF／機器人攔截）。本調查未重新驗證數字、時間範圍或主機分布；403 不應與 522 合併推論。

## 倉庫證據與涵蓋範圍

- `wrangler.jsonc:3-5` 指定 `fursay` Worker 和 `src/worker.js`；`wrangler.jsonc:16-20` 指定 `fursay-optimized-site`、`ASSETS`、`html_handling: none` 與 `run_worker_first: true`。整份設定（`wrangler.jsonc:1-28`）沒有 `routes`、`route`、自訂網域或 `workers_dev` 宣告；這不代表 Cloudflare 上沒有另行設定，也不能判定 workers.dev 實際狀態。
- 部署文件將 `https://fursay.com` 列為正式站並說明使用 Workers Static Assets（`docs/cloudflare-deploy-runbook.md:3-11`）；首頁的社群網址也是 apex（`fursay-optimized-site/index.html:10-15`）。這些是預期，不是線上綁定證明。
- 請求**進入此版本 Worker 後**，程式按路徑處理 API、短連結及 `.html`，其他請求交給資產處理，沒有 hostname 選擇或 www 轉向（`src/worker.js:1-41`）。根路徑資產查找會在首次 404 時嘗試 `/index.html`（`src/worker.js:299-311`），倉庫亦有首頁（`fursay-optimized-site/index.html:1`）。沒有看到根路徑主動 fetch 外部來源；仍不能據此排除部署版本、平台或其他 Cloudflare 設定問題。
- apex `fursay.com/`、`www.fursay.com/`、任何實際存在的舊子網域及 workers.dev／Pages 網址的線上路由都無法由此倉庫確認。特別是若路由只涵蓋特定主機或路徑，其他主機或路徑可能落到 DNS 指向的來源；不能假定 www 或任何舊子網域確實存在。倉庫搜尋未找到 `CNAME` 或 `_redirects` 檔案，也未在 docs、scripts、src 或 Wrangler 設定中找到具體 Pages／workers.dev 網址或 www 綁定。`fursay-optimized-site` 是目前資產目錄，而其名稱本身不是 Pages 部署證據（`docs/site-architecture.md:3-6`）。實際 DNS 記錄、來源 IP、代理狀態及 Pages 專案均未驗證。

## 假設（依調查優先順序，非已證實原因）

1. 某個實際請求主機或路徑沒有命中 Worker，自代理 DNS 記錄落到無法連線的來源；先以 522 的 host、路徑與時間確認，尤其區分 apex、www 和其他主機。
2. apex 本身的線上路由、自訂網域、環境或部署版本與倉庫預期不一致，或存在更特定的路由／規則改變請求處理。
3. 舊 DNS、Pages 綁定或其他 Cloudflare 規則／來源設定仍參與流量；目前沒有證據證明它們存在。若主機與路由都正確，檢查平台事件、來源與請求紀錄，不將 522 直接歸因於應用程式。

## 操作者接下來的唯讀檢查

以下由有權限的操作者在線上執行；本次沒有執行 API、DNS 查詢或網路請求。

1. Cloudflare Dashboard 的 Analytics／Logs 或 GraphQL：選取原始相同 7 天時間與時區，篩選 `edgeResponseStatus = 522`、`clientRequestPath = "/"` 和 HTML 請求；依 `clientRequestHTTPHost` 分組計數，並查看時間、路徑、Ray ID、colo、來源狀態及可用的 Worker／服務資訊。比較 403 和成功請求的 host 分布。實際可用欄位及資料保留期依帳號方案而定，避免把採樣數誤當完整計數。
2. Dashboard → DNS → Records：列出 `fursay.com`、`www`、wildcard 和所有相關子網域的類型、目標、代理狀態及 TTL；核對是否指向舊來源或 Pages。不要公開不必要的來源 IP。
3. Dashboard → Workers & Pages → `fursay`：查看正式環境的 Custom Domains、Routes、workers.dev 狀態、目前部署與版本；再到 zone 的 Workers Routes 檢查所有模式及較特定或排除規則，確認 `/` 與受影響 host 的實際命中。檢查 Pages 專案及自訂網域有無舊綁定，並檢視可能影響這些主機的 Redirect Rules、Origin Rules 與其他路由設定。
4. 使用已登入且具有唯讀權限的 Wrangler，於專案目錄執行 `npx wrangler deployments list` 及 `npx wrangler routes list`；若安裝版本不支援後者，使用 `npx wrangler --help` 和 Dashboard 的 Workers Routes 列表，不以部署命令替代。比對部署時間、版本及每個實際路由；上述命令會連網，且只供後續操作者使用。
5. 用 522 的 Ray ID 和時段對照 Cloudflare 請求紀錄及平台狀態；若可取得，確認請求是否執行 Worker、是否嘗試連線來源。保留證據後再判斷原因。

## 建議修正（須先確認證據）

- 若確認預期 host／路徑漏接，規劃正確的 Worker 路由或自訂網域，並檢查衝突與回復方案；**任何 DNS／路由變更都需要 Arthur 事先批准**。
- 若確認 DNS 指向失效來源或有舊 Pages 綁定，先盤點依賴與流量，再規劃更正或移除；**任何 DNS／路由變更都需要 Arthur 事先批准**。
- 若實際部署版本或規則不符，先比對變更歷史並提出具體修復與驗證方案；**若方案觸及 DNS／路由，需要 Arthur 事先批准**。修正後按 host 和 `/` 重查狀態及 522 趨勢。
